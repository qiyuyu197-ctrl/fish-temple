## 相册：770 张

照片从手机导进来，走一条离线管线（`tools/album-pull.ps1` + `tools/album-build.py`）：

1. 拉取原始文件，按内容哈希去重（同一张导两次不会变成两张）
2. 读 EXIF，取出拍摄时间与机型；没有 EXIF 就退回文件时间
3. 长边缩放到统一尺寸、压到目标质量，生成 `album-001.jpg … album-770.jpg`
4. 汇总成 `data/album.json`：每张记录文件名、日期、机型、宽高、字节数

前台三件事：进入画廊**自动随机抽一张**显示在大图里、灯箱可翻页可键盘操作、一键把 770 张全部展开成单列（默认是分组双列，避免一屏拉出上万像素）。

> [!NOTE]
> HEIC 是这条路线上唯一的坑：解码 HEIC 需要额外二进制，纯 Pillow 环境读不了。
> 处理方式是**跳过而不是假装成功**——导入脚本会把无法解码的文件列出来，让人工决定。

## 随机插画：为什么不能直连 Pixiv

国内网络下 `pixiv.net` / `i.pximg.net` / `pixiv.cat` 都被 DNS 污染，直连必然失败；就算能连，Pixiv 还有 Referer 防盗链。所以站点把这件事拆成三段：

```
浏览器 → /api/pixiv/random（本站服务端）→ api.lolicon.app/setu/v2   （取作品元数据）
浏览器 → /api/pixiv/image?url=…（本站服务端）→ pixiv.re 镜像        （取图片字节）
```

- **代理取图**：图片经本站转发，白名单只允许镜像域名——它不会变成开放代理
- **磁盘缓存**：取回来的图落在 `data/.cache/pixiv-img`，最多 600 张；命中缓存是毫秒级
- **抽卡池**：一次向上游要一批（`num` 上限实测是 20，写 21 直接返回 0 条），逐张发放，发过的记进 `served`，池子见底再补货——所以连着抽不会反复抽到同几张
- **预热**：启动后台把「已缓存」的图维持在水位 24 张左右，连点三次也是秒开

实测效果：单张冷加载从 33 秒降到 0.1 秒级。

## 速度是怎么救回来的

| 问题 | 处理 |
| --- | --- |
| 单张 621KB，冷加载 20–40 秒 | 换 540px 小图（约 43KB），再叠磁盘缓存 |
| 抽来抽去老是那几张 | 上游结果缓存 3 分钟 → 改成发完即弃的池子 + `served` 去重 |
| 缓存命中的图排在后面 | 发图时**优先给已缓存的**，冷图后台补 |

## 不做的事

不做 Pixiv 登录、不抓私密内容、不绕过 R18 限制；只读公开随机作品接口。数据源是可插拔的——想换成别的图库，实现一个 `endpoint` 注册进 `Registry.addImageProvider` 就行。
